\section{Contexte et motivation}
% ════════════════════════════════════════════════════════════════════════════

\subsection{Problématique clinique}

Les procédures percutanées guidées par imagerie — biopsies hépatiques, drainages, ablations par radiofréquence — requièrent une précision millimétrique et une stabilité de positionnement soutenue. Le clinicien doit simultanément manœuvrer la sonde échographique, maintenir la trajectoire d'aiguille, et interpréter l'image en temps réel. Cette charge cognitive élevée est une source documentée d'erreurs de ciblage.

\begin{keybox}{Objectif du projet}
Développer et valider en simulation un système permettant de positionner automatiquement un robot Franka \FR{} — monté sur un rail linéaire d'1,9\,m — à la position optimale pour atteindre un point anatomique cible avec la \textbf{manipulabilité maximale}, avant que le clinicien ne commande le mouvement du bras.
\end{keybox}

\subsection{Contraintes du cahier des charges}

\begin{itemize}[leftmargin=2em, itemsep=3pt]
  \item Le système doit être \textbf{compatible avec le matériel physique existant} : le robot et le rail sont déjà construits.
  \item L'interface utilisateur doit être \textbf{transparente pour le médecin} : la logique de positionnement rail est entièrement automatique.
  \item La validation doit se faire intégralement en simulation \ros{} 2 + Gazebo avant tout essai matériel.
  \item La sonde échographique est un outil personnalisé (masse 0,3\,kg, longueur TCP 0,2\,m) — aucun préhenseur standard.
\end{itemize}

\section{Modélisation URDF et contrainte du plugin Franka}

\subsection{Architecture URDF initiale et le problème découvert}

La conception initiale plaçait le robot comme un sous-arbre de la table (joint prismatique rail dans la chaîne cinématique principale). Cette approche, naturelle du point de vue de la description URDF, s'est heurtée à une contrainte interne du plugin Gazebo de Franka.

\begin{warnbox}{Contrainte critique : \texttt{franka\_ign\_ros2\_control}}
Le plugin \texttt{IgnitionSystem} de Franka construit automatiquement une chaîne KDL depuis le lien \texttt{world} jusqu'au \textit{tip link} du robot, et \textbf{impose exactement 7 joints rotatifs}. Toute présence d'un joint prismatique dans la chaîne provoque une erreur fatale :
\begin{lstlisting}[language=bash, numbers=none]
  gravity_torques(7) -- mismatch with prismatic joint in KDL chain
  [cartesian_commander] Segmentation fault (core dumped)
\end{lstlisting}
Ce comportement est documenté dans le code source de \texttt{franka\_ign\_ros2\_control} :
\begin{lstlisting}[language=cpp, numbers=none]
  // findTipLink() scans world→tip, hardcodes gravity_torques(7)
  Eigen::VectorXd gravity_torques(7);
\end{lstlisting}
\end{warnbox}

\subsection{Solution : découplage URDF et modèle Gazebo à deux entités}

La solution retenue découple entièrement la description cinématique du robot de la logique de positionnement rail.

\subsubsection{URDF modifié (\file{srr.xacro})}

Le joint \texttt{world\_to\_arm} attache directement le robot à \texttt{world} avec un offset $z = 1{,}04$\,m fixe, sans joint prismatique :

    <child  link="${arm_id}_link0"/>

Le paramètre $y$ est passé au moment du \textit{spawn} Gazebo, non dans l'URDF.

\section{Carte de capacité du robot}

\subsection{Principe général et motivation}

La carte de capacité constitue le cœur de l’approche proposée. Elle est utilisée afin de répondre à un problème fondamental : pour une cible anatomique donnée, toutes les positions du robot dans son espace de travail ne permettent pas d’obtenir une cinématique inverse valide ni une qualité de mouvement équivalente.

Ainsi, la carte de capacité permet de :
\begin{itemize}
  \item quantifier \textbf{la faisabilité cinématique} dans l’espace de travail ;
  \item comparer différentes positions du robot sur le rail ;
  \item sélectionner la position optimisant la qualité du mouvement (éviter singularités) ;
  \item garantir un comportement robuste en temps réel.
\end{itemize}

Chaque voxel est associé à deux métriques :

\begin{itemize}
  \item \textbf{Accessibilité} $\mathrm{acc}(\mathbf{p})$ : pourcentage de configurations articulaires atteignables par la cinématique inverse ;
  \item \textbf{Manipulabilité moyenne} $\bar{\mathcal{M}}(\mathbf{p})$ : moyenne de la manipulabilité sur les configurations atteintes.
\end{itemize}

L’accessibilité représente donc directement la \textbf{proportion de configurations du robot permettant d’atteindre la pose cible depuis un voxel donné}.

La manipulabilité est définie par :

\begin{equation}
  \mathcal{M}(\mathbf{q}) = \prod_{i=1}^{6} \sigma_i(\mathbf{J}(\mathbf{q}))
\end{equation}

où $\sigma_i$ sont les valeurs singulières du jacobien $\mathbf{J}$.

\begin{techbox}{Interprétation}
Une manipulabilité élevée correspond à une configuration éloignée des singularités, garantissant une meilleure précision et une meilleure isotropie des mouvements.
\end{techbox}

---

\subsection{Modèle robot et espace atteignable}

Le robot est modélisé via une chaîne cinématique DH du Franka Panda :

\begin{itemize}
  \item 7 articulations rotoïdes ;
  \item un outil prolongé de $0{,}20$\,m selon l’axe $Z$.
\end{itemize}

La portée maximale est définie par :

\begin{equation}
  \text{reach}_{\max} = \text{reach}_{\text{robot}} + \text{tool\_length}
\end{equation}

Tout voxel vérifiant $\|\mathbf{p}\| > \text{reach}_{\max}$ est exclu a priori afin de réduire le coût de calcul.

---

\subsection{Définition et justification de l’espace de travail}

L’espace de travail a été défini de manière à représenter fidèlement les contraintes d’une procédure percutanée guidée par imagerie :

\begin{itemize}
  \item zone latérale correspondant à la position du patient ;
  \item profondeur réaliste pour les accès d’aiguille ;
  \item hauteur limitée par l’ergonomie d’une table clinique ;
  \item couverture complète du volume utile du bras FR3.
\end{itemize}

La discrétisation retenue est la suivante :

\begin{center}

\rowcolor{LightBlue}
\textbf{Axe} & \textbf{Intervalle} & \textbf{Pas} & \textbf{Points} \\
\midrule

Cet espace a été choisi pour :
\begin{itemize}

  \item assurer un compromis entre précision et coût de calcul ;
  \item permettre une exploitation temps réel de la carte ;
  \item représenter une approximation d’un volume anatomique moyen d’intérêt clinique pour les procédures percutanées guidées par imagerie.
\end{itemize}

\subsection{Échantillonnage des orientations}

Pour chaque voxel, l’orientation de la sonde est échantillonnée afin de couvrir uniformément la sphère des directions possibles.

\paragraph{Méthode de Fibonacci}

Les directions unitaires sont générées via une \textbf{spirale de Fibonacci}, choisie car elle fournit une distribution quasi-uniforme sur la sphère sans clustering ni biais angulaire :

\begin{equation}
z_i = 1 - \frac{2i}{N-1}, \quad
\theta_i = \frac{2\pi i}{\phi}, \quad
r_i = \sqrt{1 - z_i^2}
\end{equation}

Cette méthode est préférée aux grilles angulaires classiques car elle garantit une homogénéité d’échantillonnage importante avec un nombre réduit de points.

---

\paragraph{Conversion en angles d’Euler}

Les directions issues de la sphère ont ensuite été converties en angles d’Euler afin d’être compatibles avec le module de cinématique inverse utilisé (\texttt{roboticstoolbox} de Peter Corke).

Chaque matrice de rotation est construite puis convertie :

\begin{equation}
R \rightarrow (\alpha, \beta, \gamma)
\end{equation}

Cette étape est indispensable car le solveur IK exploite directement des représentations en Euler.

---

\paragraph{Rotation propre}

Pour chaque direction, une rotation autour de l’axe de la sonde est ajoutée :

\begin{equation}
\gamma \in \{0^\circ, 90^\circ, 180^\circ, 270^\circ\}
\end{equation}

On obtient ainsi $N_{\text{poses}} = 200 \times 4 = 800$ poses par voxel.

---

\subsection{Construction des orientations}

Pour chaque direction $\mathbf{d}$, une base orthonormée est construite :

\begin{itemize}
  \item $\mathbf{z} = \mathbf{d}$
  \item $\mathbf{y} = \mathbf{z} \times \mathbf{r}$
  \item $\mathbf{x} = \mathbf{y} \times \mathbf{z}$
\end{itemize}

La matrice de rotation est alors :

\begin{equation}
R = [\mathbf{x} \ \mathbf{y} \ \mathbf{z}]
\end{equation}

---

\subsection{Optimisation et warm-start IK}

Les orientations sont triées selon :

\begin{equation}
|\alpha| + |\beta| + |\gamma|
\end{equation}

afin de minimiser les variations entre deux appels successifs du solveur.

\begin{techbox}{Warm-start IK}
La solution précédente $\mathbf{q}_k$ est utilisée comme initialisation pour $\mathbf{q}_{k+1}$, ce qui améliore fortement la convergence du solveur Levenberg–Marquardt et réduit les échecs de convergence.
\end{techbox}

---

\subsection{Algorithme de génération}

\begin{lstlisting}[language=python, caption={Génération de la carte de capacité (IK + manipulabilité)}]
for z in Z_vals:
    for x in X_vals:
        for y in Y_vals:
            voxel = np.array([x, y, z])

            if np.linalg.norm(voxel) > reach_max:
                continue

            reachable = 0
            manips = []
            q_prev = np.zeros(7)

            for ax, ay, az in euler_angles:
                R_base = SE3.Rx(ax) * SE3.Ry(ay) * SE3.Rz(az)

                for gamma in gamma_angles:
                    T_target = SE3(*voxel) * R_base * SE3.Rz(gamma)

                    sol = panda.ikine_LM(T_target, q0=q_prev)

                    if sol.success:
                        q_prev = sol.q
                        reachable += 1

                        J = panda.jacob0(sol.q)
                        s = np.linalg.svd(J, compute_uv=False)
                        manips.append(np.prod(s))

            acc = 100 * reachable / total
            manip_avg = np.mean(manips)
\end{lstlisting}

\section{Cinématique inverse sous contrainte de collision et relâchement d'orientation}

\subsection{Motivation clinique}

Dans le cadre des interventions percutanées assistées par robot, l’objectif principal est d’atteindre une \textbf{position cible précise dans le volume anatomique d’intérêt}, plutôt que de contrôler strictement l’orientation de l’outil.

En effet, plusieurs orientations de l’instrument restent cliniquement équivalentes tant que la trajectoire d’accès est respectée et que les tissus critiques sont évités.  
Relâcher la contrainte d’orientation permet donc :
\begin{itemize}
  \item d’augmenter l’espace des solutions cinématiques admissibles,
  \item d’améliorer la robustesse de la résolution de l’IK,
  \item de réduire le taux d’échec du solveur dans des environnements contraints.
\end{itemize}

---

\subsection{Cinématique inverse relaxée (contrainte de position)}

La cinématique inverse est formulée en ne contraignant que la position cartésienne de l’effecteur :

\begin{equation}
\mathbf{w} = [1, 1, 1, 0, 0, 0]
\end{equation}

Ce choix implique :
\begin{itemize}
  \item une contrainte stricte sur la position $(x,y,z)$,
  \item une liberté totale sur les trois angles d’orientation.
\end{itemize}

\begin{techbox}{Intérêt du relâchement d’orientation}
Le relâchement des contraintes orientationnelles permet :
\begin{itemize}
  \item d’augmenter significativement le nombre de solutions cinématiques possibles,
  \item de limiter les échecs de convergence du solveur IK,
  \item d’améliorer la robustesse globale dans un environnement fortement contraint.
\end{itemize}
\end{techbox}

---

\subsection{Modélisation simplifiée de l’environnement patient}

Le patient est modélisé par une boîte englobante axis-alignée (AABB), représentant une approximation de la zone anatomique d’intérêt :

\begin{itemize}
  \item centre : $\mathbf{c} = (0.2, 0.0, 0.1)$,
  \item dimensions :
  \begin{itemize}
    \item largeur : $0.4$ m,
    \item longueur : $1.7$ m,
    \item hauteur : $0.2$ m.
  \end{itemize}
\end{itemize}

Cette modélisation correspond à une \textbf{approximation moyenne de l’anatomie humaine d’intérêt clinique}, notamment dans le cadre d’interventions guidées sur rail.

Une configuration est considérée en collision si une partie du robot pénètre dans ce volume :

\begin{equation}
\mathbf{T}_i(\mathbf{q}) \in \mathcal{B}_{patient}
\end{equation}

où $\mathbf{T}_i(\mathbf{q})$ représente la position des différents liens du robot.

---

\subsection{Détection de collision simplifiée}

La détection de collision repose sur un test géométrique de type boîte englobante :

\begin{equation}
|x - c_x| \leq \frac{w}{2}, \quad
|y - c_y| \leq \frac{l}{2}, \quad
|z - c_z| \leq \frac{h}{2}
\end{equation}

\begin{warnbox}{Remarque sur le modèle}
Ce modèle de collision est volontairement simplifié afin de permettre une évaluation rapide lors de la recherche de solutions IK.  
Il privilégie la vitesse de calcul plutôt que la précision anatomique fine.
\end{warnbox}

---

\subsection{Recherche multi-initialisations}

Afin d’améliorer la robustesse de la cinématique inverse, plusieurs initialisations aléatoires sont testées :

\begin{itemize}
  \item 20 configurations initiales : $\mathbf{q}_0 \sim \mathcal{U}(-1,1)$,
  \item résolution via le solveur de Levenberg–Marquardt (\texttt{ikine\_LM}).
\end{itemize}

Cette stratégie permet de limiter la dépendance à l’initialisation et d’explorer plusieurs bassins de convergence.

---

\subsection{Algorithme de sélection}

\begin{lstlisting}[language=python, caption={IK avec collision et multi-start}]
best_q = None
best_score = -inf

for i in range(20):
    q0 = random_uniform(-1, 1, 7)

    sol = panda.ikine_LM(
        T_target_world,
        q0=q0,
        mask=[1,1,1,0,0,0],
        ilimit=200
    )

    if not sol.success:
        continue

    if collision(sol.q):
        continue

    J = panda.jacob0(sol.q)
    score = np.prod(np.linalg.svd(J, compute_uv=False))

    if score > best_score:
        best_q = sol.q
        best_score = score
\end{lstlisting}

---

\subsection{Critère d’optimalité}

Parmi toutes les solutions admissibles, la configuration retenue est celle maximisant la manipulabilité :

\begin{equation}
\mathcal{S}(\mathbf{q}) = \prod_{i} \sigma_i(\mathbf{J}(\mathbf{q}))
\end{equation}

Ce critère favorise les configurations éloignées des singularités et offrant une meilleure isotropie de mouvement.

---

\subsection{Résultats et robustesse}

\begin{resultbox}{Comportement observé}
\begin{itemize}
  \item augmentation significative du taux de succès de la cinématique inverse,
  \item élimination systématique des configurations en collision,
  \item sélection automatique des configurations les plus manipulables.
\end{itemize}
\end{resultbox}

---

\subsection{Conclusion de la stratégie}

La stratégie proposée combine quatre éléments complémentaires :
\begin{itemize}
  \item relâchement des contraintes d’orientation,
  \item exploration stochastique de l’espace articulaire,
  \item filtrage géométrique par collision,
  \item optimisation par manipulabilité.
\end{itemize}

Cette approche constitue une solution robuste et adaptée aux environnements fortement contraints, notamment dans un contexte d’assistance robotique médicale.

\section{Cinématique inverse multi-amorce}

\subsection{Problème de la cinématique inverse du FR3}

Le FR3 est un robot à 7\,DDL : la redondance implique une infinité de solutions IK pour une même pose TCP. Le solveur KDL (\texttt{ChainIkSolverPos\_NR\_JL}) est itératif et sensible à l'initialisation : une mauvaise amorce peut converger vers une configuration singulière ou hors-limites articulaires.

\subsection{Solution : stratégie multi-amorce avec validation FK}

\begin{lstlisting}[language=cpp, caption={Extrait cartesian\_commander.cpp — IK multi-amorce}]
  // 3 amorces candidates
  std::vector<KDL::JntArray> seeds = {
      current_q_,   // configuration courante (continuite)
      Q_HOME,       // pose home (bras baisse)
      Q_READY,      // pose ready (bras leve, operationnel)
  };

  KDL::JntArray best_q;
  double best_cost = std::numeric_limits<double>::max();

  for (auto& seed : seeds) {
      KDL::JntArray q_sol(7);
      int ret = ik_solver_->CartToJnt(seed, target_frame, q_sol);
      if (ret < 0) continue;

      // Validation par FK (seuil 3 mm)
      KDL::Frame fk_result;
      fk_solver_->JntToCart(q_sol, fk_result);
      if ((fk_result.p - target_frame.p).Norm() > 3e-3) continue;

      // Critere : deplacement articulaire minimal
      double cost = (q_sol.data - current_q_.data).norm();
      if (cost < best_cost) {
          best_cost = best_q = q_sol;
      }
  }
\end{lstlisting}

\begin{keybox}{Bénéfices de l'approche multi-amorce}
\begin{itemize}[leftmargin=1em, itemsep=2pt]
  \item \textbf{Robustesse} : si une amorce diverge, les deux autres servent de secours
  \item \textbf{Continuité} : l'amorce \texttt{current\_q\_} privilégie les mouvements courts (moins d'énergie)
  \item \textbf{Sécurité} : la validation FK garantit que la solution IK atteint effectivement la cible
  \item \textbf{Élimination de la dérive} : évite les configurations où le robot atteint la position mais pas l'orientation (problème observé avec amorce unique)
\end{itemize}
\end{keybox}

\subsection{Publication de la pose TCP en frame monde}

Pour fermer la boucle avec le GUI, \texttt{cartesian\_commander} publie en permanence la pose du TCP convertie en frame monde :

\begin{equation}

  =
  \begin{pmatrix} x_r \\ y_r + (-0{,}85 + p_{\text{rail}}) \\ z_r + 1{,}04 \end{pmatrix}_{\text{TCP}}
\end{equation}

Le GUI affiche automatiquement ces valeurs et pré-remplit ses champs de saisie dès réception du premier message sur \topic{/current\_tcp\_pose}.

  Auto-remplissage       & Les champs se pré-remplissent avec la pose TCP courante en frame monde \\
  Bouton refresh         & Recharge la pose TCP courante à la demande \\
  Saisie RPY             & Entrée en degrés (roll, pitch, yaw), conversion quaternion automatique \\
  Affichage quaternion   & Mise à jour en temps réel lors de la saisie des angles \\
  Durée de mouvement     & Paramétrable (défaut : 5\,s) \\
  Indicateur busy        & Bouton désactivé pendant un mouvement ; barre de statut colorée \\
  \bottomrule
\end{tabular}
\end{center}

La conversion Euler (degrés, convention RPY extrinsic) $\leftrightarrow$ quaternion est implantée directement dans le nœud pour éviter toute dépendance externe :

\begin{equation}
  q_w = c_r c_p c_y + s_r s_p s_y, \quad
  q_x = s_r c_p c_y - c_r s_p s_y
\end{equation}
\begin{equation}
  q_y = c_r s_p c_y + s_r c_p s_y, \quad
  q_z = c_r c_p s_y - s_r s_p c_y
\end{equation}

\section{Discussion et perspectives}
% ════════════════════════════════════════════════════════════════════════════

\subsection{Contributions techniques principales}

\begin{enumerate}[leftmargin=2em, itemsep=6pt]
  \item \textbf{Découverte et contournement de la contrainte KDL du plugin Franka} : identification que \texttt{franka\_ign\_ros2\_control} impose une chaîne purement rotoïde de 7 joints, avec développement de l'architecture URDF découplée.

  \item \textbf{Carte de capacité pré-calculée} : génération d'une grille 3D de 2235 voxels avec évaluation de 800 poses IK par voxel, permettant une sélection rail en temps réel ($<$\,5\,ms).

  \item \textbf{Mission coordinator} : orchestration ROS\,2 complète (rail + bras) avec gestion des timeouts, retour d'état au GUI, et conversion de repère automatique.

  \item \textbf{IK multi-amorce avec validation FK} : amélioration de la robustesse de la cinématique inverse par essai de 3 configurations initiales avec critère de déplacement articulaire minimal.
\end{enumerate}

\subsection{Limitations actuelles}

\begin{warnbox}{Limitation principale : mouvement visuel du robot dans Gazebo}
La physique Gazebo combinée à \texttt{ros2\_control} s'oppose aux commandes \texttt{ign service set\_pose} sur le modèle \texttt{probo11}. L'IK est correctement calculée pour la position rail cible, mais la visualisation du robot dans Gazebo ne reflète pas le déplacement du rail.

\textbf{Solution envisagée — Option A (re-spawn)} : interrompre les contrôleurs, supprimer et re-spawner le modèle à la nouvelle position, relancer les contrôleurs. Complexe mais visuellement complet.

\textbf{Solution envisagée — Option B (matériel réel)} : en production, le robot se déplace physiquement sur le rail ; la limitation est propre à la simulation Ignition Gazebo 6.
\end{warnbox}

\subsection{Perspectives}

\subsubsection{Intégration sur matériel physique}

Le système est conçu pour la transition simulation $\to$ réel :
\begin{itemize}[leftmargin=1.5em, itemsep=2pt]
  \item \texttt{cartesian\_commander} pilote le vrai FR3 via \texttt{franka\_hardware} (même interface ros2\_control)
  \item \texttt{rail\_mover} peut être adapté pour piloter un actionneur linéaire via un topic de commande
  \item La carte de capacité est indépendante du simulateur
\end{itemize}

\subsubsection{Améliorations algorithmiques}

\begin{itemize}[leftmargin=1.5em, itemsep=2pt]
  \item Intégration de contraintes d'évitement d'obstacles dans la sélection rail
  \item Prise en compte de la résolution angulaire de la sonde (pas seulement position)
  \item Raffinement continu de la carte par interpolation (résolution sous-voxel)
  \item Ajout de la contrainte d'accessibilité ($\mathrm{acc} > \text{seuil}$) en plus de la manipulabilité
\end{itemize}

\subsubsection{Extension à d'autres procédures}

Le cadre développé — carte de capacité + sélecteur rail + mission coordinator — est générique et peut être réutilisé pour d'autres procédures nécessitant un positionnement robotique optimal.

\section*{Conclusion}
\addcontentsline{toc}{section}{Conclusion}
% ════════════════════════════════════════════════════════════════════════════

\begin{keybox}{Bilan du projet PROBO-11}
Le projet PROBO-11 a développé et validé en simulation \ros{} 2 + Gazebo un système complet de positionnement automatique d'un robot FR3 sur rail linéaire pour procédures percutanées. Les contributions clés sont :

\begin{itemize}[leftmargin=1em, itemsep=3pt]
  \item Architecture URDF découplée contournant la contrainte KDL du plugin Franka
  \item Carte de capacité pré-calculée (2235 voxels, 800 poses IK/voxel) pour sélection rail en temps réel
  \item Orchestration ROS\,2 complète avec \texttt{mission\_coordinator} gérant la séquence rail $\to$ bras
  \item Interface GUI clinique intuitive avec retour de pose TCP en frame monde
  \item IK multi-amorce améliorant la robustesse face aux singularités
\end{itemize}

Le système est prêt pour la validation sur matériel physique, les nœuds ROS\,2 étant agnostiques vis-à-vis du simulateur.
\end{keybox}
